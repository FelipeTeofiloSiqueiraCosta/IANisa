# Ratoeira multiusuário: scripts e units de root

Um usuário Linux por pessoa, um servidor de agentes por usuário (chat, terminal e Contas de IA), num socket que só o gateway abre. Aqui ficam os scripts e as units de root que sustentam isso. Nenhum roda direto desta pasta: o `publicar-core` instala cada um no lugar dele.

## Onde cada coisa mora

- **Núcleo, em `/opt/ratoeira`:** o gateway (`/opt/ratoeira/gateway`) e o servidor de agentes (`/opt/ratoeira/agentes`), cada um um atalho pra uma pasta de versão em `/opt/ratoeira/versoes/<parte>/` (ficam a do ar e as 3 anteriores); o Claude Code e o Codex da máquina, em `/opt/ratoeira/bin`, os mesmos pra todo mundo; os apps publicados, em `/opt/ratoeira/apps/<nome>`; e o que as receitas instalam (Playwright, navegadores, ditado).
- **Fonte do produto, em `/opt/ratoeira/fonte`** (nas instalações): o clone do repositório do produto, do root, na versão que está no ar. É dela que sai tudo que o núcleo instala.
- **Scripts e units desta pasta:** em `/usr/local/sbin`, `/usr/local/lib/ratoeira`, `/usr/local/bin` e `/etc/systemd/system` (a lista exata é o `KIT` do `publicar-core`). As units já vêm com os caminhos do produto; máquina com outro caminho ou outro grupo muda por drop-in (`<unit>.d/local.conf`), que vale por cima da unit.
- **Fica com a instalação, a atualização não mexe:** a configuração em `/etc/ratoeira` (a config do gateway só muda por migração, com cópia antes), o estado do gateway em `/var/lib/ratoeira/gateway-estado`, as áreas em `/srv/ratoeira/areas/<id>`, os dados dos apps em `/var/lib/ratoeira/apps` e as homes.

## Instalar e atualizar

A instalação do zero mora em `../instalador`. O `instalar.sh` prepara a VPS, clona o produto em `/opt/ratoeira/fonte`, cria a pessoa que administra e a área de trabalho (com o `adicionar-pessoa.sh` e o `criar-area.sh` daqui), grava a config inicial e os drop-ins e monta o núcleo pelo mesmo atualizador das versões novas. A conversa com a pessoa (o que pedir, o que explicar) fica na `../instalador/RECEITA.md`, que o agente dela conduz.

Quem troca o código é o `publicar-core`, por parte:

| Parte | O que faz |
|---|---|
| `telas` | troca `gateway/public` dentro da versão do gateway que está no ar (vale no próximo recarregar da página) |
| `gateway` | monta o gateway numa pasta de versão nova (`npm ci` + `build:chat`), aponta o atalho pra ela e reinicia; se não responder, volta pra anterior |
| `agentes` | monta o servidor de agentes numa pasta de versão nova; o de cada pessoa religa quando fica livre |
| `regras` | instala o texto fixo dos agentes (`kit/agentes.md`, `kit/ratoeira-instrucoes`, `APPS.md`) e as skills do produto (`kit/skills`) em `/usr/local/lib/ratoeira` e roda o `ratoeira-instrucoes` |
| `kit` | instala os scripts e as units desta pasta |
| `receita` | roda como root um script de `../receitas/<nome>` (até 3 argumentos) |
| `pacotes` | `apt-get install` de até 20 pacotes |

Sempre publica o que está commitado na fonte (`HEAD`), com o git e o npm rodando como o usuário do gateway, e guarda o que trocou.

- **Nas instalações**, quem chama é o atualizador (`../instalador/atualizar`, o comando `ratoeira-atualizar`, que o botão de Configurações › Atualizações aciona): a partir de `/opt/ratoeira/fonte`, na ordem `kit`, `regras`, `agentes`, `gateway`. O que o `publicar-core` não instala de propósito (ele mesmo e a unit dele, a regra do polkit, o atualizador e as units dele, a unit do gateway) vai pelo passo "sistema" do atualizador. A config nasce com `"core": {"fonte": "/opt/ratoeira/fonte", "partes": []}`: nada se publica pelo chat. Receita roda pelo instalador ou à mão: `sudo bash /opt/ratoeira/fonte/kit/receitas/<nome>`.
- **Onde a Ratoeira é desenvolvida**, um admin publica pelo chat (`publicar_ratoeira`, `rodar_receita`, `instalar_pacotes`): a config aponta `core.fonte` pra pasta da Ratoeira dentro de uma área e lista em `core.partes` o que pode sair por ali.

## Arquivos

- `adicionar-pessoa.sh`: cria o usuário Linux e a ACL de leitura do gateway na pasta de trabalho. Roda como root, uma vez por pessoa.
- `ratoeira-adicionar@.service`: cria uma pessoa (roda o `adicionar-pessoa.sh` como root, só pra usuário novo). O gateway dá `start` nela quando o admin convida alguém com ambiente (login próprio, `criaAmbiente`). Grupo no drop-in `ratoeira-adicionar@.service.d/local.conf`.
- `ratoeira-agentes@.service`: o servidor de agentes por ACP de cada pessoa (`../../agentes`, em `/opt/ratoeira/agentes`), chat, terminal e Contas de IA. Roda como ela, sem sudo, só enxerga a própria home (e as áreas), socket em `/run/ratoeira-agentes-<usuário>/agentes.sock`. Sai sozinho depois de 30 min parado; o gateway liga quando o chat conecta (`"agentes"` na config do gateway). Vem com `DISABLE_AUTOUPDATER=1`: o Claude Code é o da máquina, e quem troca a versão é a atualização da Ratoeira.
- `conta-claude`: escolhe a conta do Claude e a do Codex (geral, própria, opcional) e roda o comando com elas. Entrega também o token do **cofre de chaves** (1Password) a quem está no grupo `ratoeira-cofre`, que o `aplicar-acessos` mantém (todo mundo com ambiente, quando o admin conectou o cofre). Claude: conta por token (organização, pessoal antiga) vai como token no ambiente; conta pessoal com login completo vai como `CLAUDE_CONFIG_DIR` apontando pra pasta dela em `~/.config/ratoeira/claude-contas/<id>/`. É a conta **padrão**: o servidor de agentes abre um processo por conta pras conversas que usam outra. Codex geral = `~/.codex/auth.json` vira atalho pro arquivo único em `/var/lib/ratoeira/codex-geral/` (por isso a unit dos agentes libera essa pasta pra escrita). Usado pelo `ratoeira-agentes@` e pelo `ratoeira-cron`.
- `commit-turno` + `managed-settings.json` (em `/usr/local/lib/ratoeira` e `/etc/claude-code`): ganchos UserPromptSubmit e Stop do Claude Code, pra todo usuário da máquina. No começo do pedido anota o que já estava modificado na pasta da conversa; no fim da resposta commita, no nome de quem pediu, o que o agente editou numa área e (desde 19/10/2026) o que mudou na pasta da conversa durante a resposta, inclusive por comando. Teste: `kit/test/test_commit_turno.py`.
- `50-ratoeira.rules`: polkit. Deixa o usuário do gateway só **ligar** e **desligar** o servidor de agentes de alguém, **criar** uma pessoa (`ratoeira-adicionar@`) e dar `start` nos ajudantes de root (acessos, automações, publicar).
- Travas: o script e a unit dos agentes recusam usuário de sistema (UID < 1000) e usuário do grupo `sudo`. **Modo confiança (o padrão):** a receita `../receitas/modo-confianca` dá sudo sem senha ao grupo `ratoeira-pessoas` (`/etc/sudoers.d/ratoeira-confianca`, sem pôr ninguém no grupo `sudo`, então as travas seguem valendo) e põe o drop-in `ratoeira-agentes@.service.d/confianca.conf`, que tira `NoNewPrivileges`, `ProtectSystem`, `ProtectHome` e `PrivateTmp`. `desligar` volta ao modo restrito.
- `playground` (em `/usr/local/sbin/ratoeira-playground`) + `ratoeira-playground.service` + `.timer`: de minuto em minuto lê os containers com a etiqueta `ratoeira.play`, grava o estado que a seção Publicados mostra (`/var/lib/ratoeira/playground/estado.json`, grupo do gateway) e desliga o programa que ficou 7 dias sem acesso. Instalados pela receita `../receitas/playground` (que tira os arquivos do último commit, porque o `publicar-core` roda a receita sozinha).
- `criar-area.sh`: transforma uma pasta (em geral um repo) em área do time em `/srv/ratoeira/areas/<id>`: grupo, ACL, git compartilhado, registro em `/etc/ratoeira/areas.json`.
- `automacoes` + `ratoeira-automacoes.service` + `.timer`: as automações de cada pessoa moram em `~/.config/ratoeira/crontab` (ela e o agente dela editam; o `crontab -e` não grava de dentro do servidor de agentes, por causa do `NoNewPrivileges`). De 1 em 1 minuto, e quando o gateway pede, o script instala esse arquivo como crontab dela (`crontab -u`), aplica o liga/desliga que o admin pediu (edição feita como a dona, via `runuser`) e grava o inventário que só o admin vê (`/var/lib/ratoeira-automacoes/inventario.json`, grupo do gateway): automações e último resultado de cada pessoa, crons de `/etc/cron.d` e de quem não é pessoa (ex.: o crontab do root), timers, e MCPs de cada um (só nome, tipo e host). O pedido do gateway fica em `<portal.dataDir>/automacoes-pedido.json` (padrão da unit: `/var/lib/ratoeira/gateway-estado/automacoes-pedido.json`); outro caminho ou outro grupo, pelo drop-in `ratoeira-automacoes.service.d/local.conf` (`RATOEIRA_AUTOMACOES_PEDIDO`, `RATOEIRA_GRUPO`).
- `ratoeira-rotina` (em `/usr/local/bin`): roda uma rotina (`~/.config/ratoeira/rotinas/<id>.md`): abre o Claude (`-p`, `--permission-mode auto`) ou o Codex (`exec --approve-for-me`) na pasta dela, e grava qual conversa nasceu e o título dela (`~/.local/state/ratoeira/titulos.json`, que o servidor de agentes relê). O `automacoes` gera a linha de cron de cada rotina.
- `ratoeira-cron` (em `/usr/local/bin`): invólucro de cada automação, `ratoeira-cron <nome> -- <comando>`. Roda com o PATH dos CLIs e as contas do Claude/Codex da pessoa (`conta-claude`) e guarda início, fim, código e log em `~/.local/state/ratoeira/crons/`.
- `publicar-app` (em `/usr/local/sbin/ratoeira-publicar-app`) + `ratoeira-publicar@.service` + `ratoeira-app@.service`: publica um app pelo botão da tela de Apps, sem sudo. O gateway grava o pedido e dá `start` em `ratoeira-publicar@<nome>`; o script, como root, valida o manifesto, cria `app-<nome>`, copia o código pra `/opt/ratoeira/apps/<nome>/codigo` (sem a ACL da área), roda o `preparar` como o app, gera o drop-in da `ratoeira-app@<nome>` e os timers das rotinas, espera a rota de saúde (volta a versão anterior se falhar) e grava o registro em `/etc/ratoeira/apps.d/<nome>.json`, que o gateway relê sem reiniciar. Pacotes só de `/etc/ratoeira/pacotes-permitidos`. Config do gateway: `"publicar": {"registro": "/etc/ratoeira/apps.d"}`.
- `publicar-core` (em `/usr/local/sbin/ratoeira-publicar-core`) + `ratoeira-publicar-core@.service`: troca o núcleo por parte (seção "Instalar e atualizar"). A unit é o caminho do chat de um admin; o atualizador chama o script direto. Não instala a si mesmo nem a regra do polkit.
- **Receitas** (`../receitas/`): scripts de instalação pra máquina toda, como root. Nas instalações rodam pelo instalador ou à mão; onde a Ratoeira é desenvolvida, também pelo `publicar-core`, quando um admin chama `rodar_receita` no chat (só do último commit). Pacote do apt sozinho: `instalar_pacotes`.
  - `playwright`: Playwright + Chromium (biblioteca em `/opt/ratoeira/playwright`, comando em `/opt/ratoeira/bin/playwright`, navegadores em `/opt/ratoeira/ms-playwright`; a unit dos agentes e o `ratoeira-cron` passam `NODE_PATH` e `PLAYWRIGHT_BROWSERS_PATH`, e `/node_modules/playwright` aponta pra biblioteca, pro `import` achar), o Google Chrome (apt) e o `playwright-cli` (`/opt/ratoeira/playwright-cli`, comando em `/opt/ratoeira/bin`), que a skill `navegador-ratoeira` ensina; o `conta-claude` põe as saídas dele em `~/.cache/ratoeira/navegador` e fecha o Chrome depois de 10 min parado. À mão: `sudo ../receitas/playwright [versão] [versão do cli]`.
  - `ditado-local` (microfone do chat sem chave nenhuma), `playground` (os programas dos Publicados, em Docker), `modo-confianca` (`ligar` ou `desligar`), `chaves-app` (as chaves de um app em `/etc/ratoeira/apps/<app>/chaves.env`) e `religar-agentes`.
  - `backup`: só atualiza o código de um backup já montado à mão (unit, timer e restic em `/etc/ratoeira-backup`). O backup ainda não vem no produto; sem a unit, a receita para e avisa.
- `ratoeira-navegador@.service` + `ratoeira-navegador` (em `/usr/local/bin`): o navegador da Ratoeira de cada pessoa (`../../agentes/navegador.mjs`): Google Chrome com tela virtual (Xvfb) e o perfil dela na home, num endereço com código secreto que só ela lê (`/run/ratoeira-navegador-<usuário>/estado.json`). O agente pede com `ratoeira-navegador` (liga se precisar e escreve o endereço pro `playwright-cli attach --endpoint`); sai sozinho 3 min depois que ninguém está conectado, fechando pelo Chrome pra gravar o login. Teto de memória próprio (1200 MB), fora das conversas. O polkit (`50-ratoeira.rules`) deixa cada pessoa ligar e desligar só o dela, e o gateway ligar e desligar qualquer um (tela ao vivo, a fazer).
- `aplicar-acessos` + `ratoeira-acessos.service`: aplica quem entra em cada área e as pastas restritas, as contas de IA da organização, o cofre, a chave do ditado e o autor dos commits de cada pessoa (`~/.gitconfig`), pelo pedido que o gateway grava em `<portal.dataDir>/contas/acessos.json` (padrão da unit: `/var/lib/ratoeira/gateway-estado/contas/acessos.json`). Outro caminho ou outro grupo, pelo drop-in `ratoeira-acessos.service.d/local.conf` (`RATOEIRA_ACESSOS`, `RATOEIRA_GRUPO`).

## À mão

- Memória por pessoa: `sudo RATOEIRA_MEMORIA=2500M ./adicionar-pessoa.sh <usuário>` grava um drop-in só dela; o padrão está na unit (`MemoryMax=1500M`).
- O gateway (`main.mjs`) roda como `ratoeira-gateway`, com `SupplementaryGroups=ratoeira-gw` (a unit é a `../instalador/ratoeira-gateway.service`). Precisa de `npm run build:chat` (gera o markdown do chat, o editor e o terminal), que a parte `gateway` do `publicar-core` já roda.
